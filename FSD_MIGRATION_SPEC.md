# Техническое задание на переход WebSynth на Feature-Sliced Design

## 1. Цель и объём работ

1. Выделить точку запуска приложения, страницу редактора и предметную модель проекта. Зафиксировать разрешённые зависимости и публичные точки входа.
2. Перенести существующие сценарии WebSynth в новую структуру с сохранением пользовательского поведения, формата данных и работы на настольном Chrome.
3. Добавить автоматическую проверку архитектурных границ и корневой `AGENTS.md` с правилами сопровождения проекта.
4. Объём работ ограничен архитектурной миграцией. Изменения интерфейса, новые аудиомодули, смена библиотек и обновление формата данных находятся за её пределами.

## 2. Целевая структура

```text
src/
  app/
    main.tsx
  pages/
    rack/
      index.ts
      ui/
      model/
      api/
      lib/
  entities/
    project/
      index.ts
      model/
tests/
AGENTS.md
WIDGET_DEVELOPMENT.md
```

1. **`app`** монтирует React, подключает `ReactFlowProvider`, библиотечные стили и публичный компонент страницы. `index.html` указывает на новый вход Vite.
2. **`pages/rack`** владеет единственным экраном приложения. В `ui` находятся редактор, узлы и кабели React Flow, каталог, меню, диалоги, окна параметров и стили экрана. В `model` находятся состояние открытого проекта, история редактирования, сценарии управления проектами, очередь автосохранения и синхронизация с движком. В `api` находится адаптер IndexedDB. В `lib` находятся аудиодвижок и браузерные операции с файлами.
3. **`entities/project`** владеет сериализуемым проектом, именованными версиями и графом патча. `Project`, `Patch`, `Module`, `Wire`, метаданные модулей и правила графа образуют один слайс на время миграции. Это позволяет сохранить общий контракт типов, портов и параметров между редактором, движком и импортом. Здесь же находятся чистые функции кодирования и проверки JSON. Типы сохранённых координат, viewport и окон остаются частью контракта патча.
4. Создавать каталоги по мере переноса кода. Добавлять `shared` для конкретной общей инфраструктуры или UI без знаний о предметной области. Выделять `widgets` и `features`, когда появляется самостоятельный блок или пользовательское действие с отдельными потребителями и понятным публичным контрактом.

## 3. Правила зависимостей и публичных API

1. Для текущей структуры разрешить `app → pages, entities` и `pages → entities`. При появлении остальных слоёв применять порядок `app → pages → widgets → features → entities → shared`. Любой слой может обращаться к более низкому слою. Импорты между соседними слайсами одного слоя и в вышележащие слои запрещены. Сегменты `app` и `shared` могут взаимодействовать внутри своего слоя.
2. Снаружи слайса импортировать только из его `index.ts`. Внутри слайса использовать прямые относительные импорты. `pages/rack/index.ts` экспортирует компонент страницы. `entities/project/index.ts` явно экспортирует типы, метаданные и операции, которые нужны внешним потребителям. В публичных точках входа использовать именованные экспорты. Для внешнего доступа к будущему сегменту `shared` определить отдельный публичный вход.
3. Проверять границы по разрешённым путям файлов. Правила распространяются на импорты типов, реэкспорты и динамические импорты с литеральным путём. Тесты предметной модели обращаются к публичному API сущности. Для браузерных адаптеров допускаются адресные тесты их собственных контрактов.
4. Сохранить совместимость импортов с Vite, TypeScript и существующим запуском тестов напрямую через Node.js. Алиасы путей не входят в требования миграции.

## 4. Порядок миграции

1. **Зафиксировать исходное поведение.** Запустить `npm test` и `npm run build`. Подготовить JSON, экспортированный текущей версией, с рабочим патчем и именованной версией. Подготовить данные IndexedDB с несколькими проектами и выбранным активным проектом. Зафиксировать результаты проверок до переноса.
2. **Отделить запуск приложения.** Перенести монтирование и провайдер в `app/main.tsx`, компонент `Rack` и стили экрана в `pages/rack/ui`. Обновить путь в `index.html` и подключить страницу через её публичный вход. Сохранить порядок загрузки стилей.
3. **Выделить модель проекта.** Перенести из `model.ts` типы, каталог модулей, генерацию идентификаторов и чистые операции. Разместить ограничения параметров из `storage.ts` рядом с метаданными модулей. Использовать их в контролах и валидаторе. Сохранить значения, шаги, типы сигналов, ID портов и правила авторасширения. Перенести из `storage.ts` разбор и проверку JSON в модель. Отделить формирование JSON от скачивания через браузер.
4. **Перенести хранение и оркестрацию.** Разместить чтение и запись библиотеки в `pages/rack/api`, а управление состоянием из `useRack.ts` в `pages/rack/model`. Сохранить порядок записей, задержку автосохранения, обработку ошибок, сброс истории при переключении проекта и попытку записи при скрытии вкладки или уходе со страницы. Оставить управление жизненным циклом экземпляра движка на уровне страницы.
5. **Перенести аудио и UI.** Разместить `AudioEngine` в `pages/rack/lib`. Движок получает данные из публичного API модели проекта. Перенести `RackModule`, `WidgetControls`, `FloatingWindow` и кабели в `pages/rack/ui`. Вынести из компонента страницы сценарии, отвечающие за изменения проекта или патча, в `pages/rack/model`. События React Flow, выбор элементов, ввод и отображение остаются в UI. Компоненты получают состояние и команды для своих действий. Граф, браузерные адаптеры и движок остаются доступными через их владельцев.
6. **Завершить перенос.** Обновить импорты тестов, ссылки в `README.md` и инструкцию `WIDGET_DEVELOPMENT.md`. Удалить старые точки входа и временные реэкспорты после перевода потребителей. Проверить тесты и сборку после каждого законченного этапа.
7. **Подключить проверку архитектуры.** Добавить команду `npm run check:architecture` и включить её в стандартный запуск `npm run build`. Проверка должна завершаться с ошибкой при импорте вверх, импорте соседнего слайса или обходе публичного API. Сообщение об ошибке указывает исходный файл, путь импорта и нарушенное правило. Проверить каждый из трёх запретов контрольным примером.
8. **Создать корневой `AGENTS.md`** по требованиям раздела 5. Сверить примеры путей, публичные API и команды с фактической структурой после миграции.

## 5. Обязательное содержание `AGENTS.md`

1. **Карта проекта.** Описать назначение `app`, `pages/rack`, `entities/project` и сегментов. Указать, где находятся граф, валидация, состояние редактора, браузерное хранение, Web Audio и Web MIDI, UI и стили. Дать ссылку на `WIDGET_DEVELOPMENT.md`.
2. **Порядок выбора места для изменения.** Перед добавлением кода найти существующего владельца и использовать его контракт. Сценарий, используемый только редактором, размещать в `pages/rack`. Правила, действующие для любого патча или проекта, размещать в `entities/project/model`. В `app` размещать подключение приложения и глобальных провайдеров. Для нового экрана создавать отдельный слайс `pages`.
3. **Правила расширения.** Описать условия появления `features`, `widgets`, новых `entities` и сегментов `shared`. Указать, что бизнес-правила проекта принадлежат предметной модели. При использовании одной логики несколькими слайсами определить общего владельца по смыслу и разместить контракт ниже потребителей. Добавлять в публичный API только то, что используется за границей слайса.
4. **Импорты.** Записать порядок слоёв, запрет межслайсовых импортов на одном слое и правило публичных входов. Привести три примера на фактических путях проекта — импорт сущности через её публичный вход, внутренний относительный импорт и запрещённый импорт внутреннего файла сущности со страницы.
5. **Новый аудиомодуль.** Описать маршрут изменения от метаданных, портов и значений по умолчанию до runtime, UI и валидации. Сослаться на подробный порядок в `WIDGET_DEVELOPMENT.md`. Зафиксировать совместимость ID портов и очистку аудиоресурсов при удалении runtime. Объяснить, что аудиоузлы, MIDI-устройства и DOM-объекты принадлежат браузерному runtime и не сериализуются.
6. **Совместимость данных.** Зафиксировать JSON `schemaVersion: 1` и контракт IndexedDB. Перед изменением сериализуемых полей проверить ранее созданные проекты, рабочий патч и все именованные версии. Для будущего несовместимого изменения определить версию и путь миграции всех затронутых данных.
7. **Проверки перед завершением.** Указать `npm test`, `npm run check:architecture` и `npm run build`. Привязать ручные проверки к области изменения. Для графа проверять маршрутизацию и undo/redo, для хранения — загрузку и повторное открытие проекта, для аудио и MIDI — затронутые сценарии в Chrome. При перемещении владельца кода обновлять ссылки в документации.

## 6. Критерии приёмки

1. `npm test`, `npm run check:architecture` и `npm run build` проходят. Все существующие проверки графа и JSON сохранены. Архитектурная проверка обнаруживает каждый запрещённый вид импорта, описанный в разделе 4.
2. Приложение запускается через Vite и открывает редактор из production-сборки. В Chrome проверены добавление, перемещение, удаление и дублирование модулей, подключение и удаление кабелей, undo/redo, горячие клавиши, панорамирование и окна параметров. Mixer и Splitter расширяются с сохранением существующих подключений. Несовместимые порты и циклы аудиографа отклоняются.
3. Осциллятор звучит через Output, изменения параметров применяются. Проверены MIDI Input → MIDI Synth → Output, выбор устройств и поведение при недоступном аудиовыходе. Для проверок, зависящих от устройства, в отчёте указать использованное оборудование или виртуальный порт. Сценарии, которые нельзя воспроизвести в доступной среде, пометить отдельно.
4. Сборка после миграции читает IndexedDB, созданную сборкой до миграции на том же origin. Сохраняются имя базы `websynth`, версия БД `1`, хранилище `library` и ключ `state`. После перезагрузки доступны активный проект, рабочий граф, viewport, окна и именованные версии. Проверены создание, переключение, переименование и удаление проекта, сохранение и восстановление версии.
5. JSON прежней версии импортируется с рабочим патчем и именованными версиями. Поддерживаются старые осцилляторы без поля `oscillators`. Экспорт сохраняет формат `schemaVersion: 1`. При повторном импорте сравниваются имена и содержимое патча и версий с учётом текущего поведения генерации ID. Некорректный JSON и недопустимые графы отклоняются с сообщением пользователю.
6. В корне есть `AGENTS.md` со всеми правилами из раздела 5. По нему можно определить, куда добавить новый модуль, где изменить правило соединения и когда выделить новый слайс. Примеры, команды и ссылки в документации соответствуют итоговому дереву.
7. К сдаче приложить перечень перемещённых модулей, результаты автоматических и ручных проверок и список сценариев, которые не удалось проверить.
